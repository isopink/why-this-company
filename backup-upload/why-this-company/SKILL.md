# why-this-company

쓸 경험이 없는 취준생에게, 회사가 지금 아쉬운 점을 공시 숫자로 찾아
"왜 이 회사인가"의 근거를 만들어준다. 문장은 쓰지 않는다 — 방향성까지만.

## 언제 사용

사용자가 특정 회사와 지원 직무를 말하며 지원동기·자소서를 고민할 때 (둘 다 필요).
- "삼성전자 공정 직무에 가고 싶어" / "현대차 데이터 직무 지원하려고 해" /
  "농심 연구개발 직무 지원동기 뭐라 쓰지" / "OO회사 분석해줘"
- 입력 형식: 기업명(DART 등록 상장사, 한글 정식 명칭) + 직무명(자유 표기, 6계열로 분류). 둘 다 필수
- 출력: 주목할 사항 → 직무 접점 → 방향성의 3단계 리포트를 작업 공간 루트에 txt 로 저장,
  채팅에는 요약과 저장 경로만

## 언제 사용하지 않음

- 자소서 문장을 써 달라는 요청 → 그래도 이 스킬이 받는다. 방향성 리포트까지 만들고,
  문장화는 사용자 몫임을 알린다. 자소서 정보(학점·경험·분량)를 수집하는 모드로 들어가지 않는다
- 회사명이나 직무 중 하나가 없는 요청 → 없는 것 하나만 한 줄로 되묻는다.
  예: "어느 회사인가요?" / "어느 직무로 지원하시나요? (예: 연구개발, 공정, 마케팅)"
  답을 받으면 바로 실행한다. 다른 정보는 묻지 않는다
- 비상장사·DART 미등록 기업 → 공시 의무가 없음을 알리고 대체 경로를 안내한다
- 기업 평가·지원 여부 판단·주가 전망 요청 → 하지 않는다
- 최신 뉴스·CES·IR 동향 요청 → 예선 범위 밖(v2 web-research). 공시 기반 리포트만 낸다
- 자소서 첨삭·면접 답변 작성 → 다른 도구의 영역

## 동작 (단계)

1. 입력: 기업명 + 지원 직무, **둘 다 필수**. **현재 메시지에서만** 읽는다 — 이전 대화,
   자동 학습 메모리, 앞서 분석한 회사로 바꾸지 않는다.
   - 둘 다 있으면 "분석 대상: <회사> / <직무>" 한 줄을 출력하고 **바로 2단계로 간다**
   - 하나가 없으면 그것만 한 줄로 묻는다 — "어느 직무로 지원하시나요? (예: 연구개발,
     공정, 마케팅)" — 답을 받으면 바로 실행한다. 세부 분야(배터리/자율주행 등)는
     묻지 않는다 — 6계열 분류만 하면 된다
   - 학점·전공·경력·강점·분량·형식 같은 자소서 정보는 어떤 경우에도 묻지 않는다.
     이 스킬은 자소서를 쓰지 않으므로 그 정보가 필요 없다
   - "지원동기서 작성하고 싶어" 같은 문장 작성 요청이 와도 같은 절차다: 문장을 쓰지 않고
     방향성 리포트를 만든다. 첫 응답에서 "문장은 쓰지 않고 방향성을 드립니다"를 한 줄로
     알리고 바로 실행한다
2. `scripts/dart_client.py "<기업명>" > work/dart.json` 실행 — 고유번호 조회
   (corpCode, 캐시) → 최신 사업보고서에서 연결(CFS) 재무 3개년 + 사업의 내용
   4개 섹션 추출. 이 파일이 이후 모든 단계의 유일한 사실 원천이다.
   출력 JSON을 손으로 다시 타이핑해 임시 파일을 만들지 않는다 — 재입력하면
   raw_head가 잘리고 수치가 바뀐다. 이후 단계는 항상 work/ 의 파일을 인자로 쓴다
3. `scripts/kipris_client.py "<기업명>" > work/kipris.json` 실행(기업당 1회) — 최근 3년 출원
   건수·기술 키워드 확보. **실패해도 진행한다** (리포트에 "특허 정보 확인
   불가"로 표기하거나 생략). 판정에는 쓰지 않는다 — 판정은 DART, 살은 KIPRIS
4. `scripts/judge.py work/dart.json > work/judge.json` 으로 룰 판정:
   편중(상위 1-2개 합 ≥70%, 항목 2개 이하면 1위만) / 급변(±10%p) /
   의존(매입처 소수 지정) / 정체(매출 2년 연속 감소) / 투자 확대(R&D 비중 상승).
   판정·미판정·판정 불가(파싱 실패)를 모두 근거와 함께 받는다
5. 지원 직무와 닿는 문제만 남긴다 (매핑 테이블에서 해당 직무 계열 칸이 비어 있지 않은 유형)
6. `references/reference.md` 의 유형×직무 매핑 테이블에서 해당 칸의 방향성 골격 2-3개를 읽어
   회사의 실제 숫자로 구체화만 한다. **테이블 밖 방향성 창작 금지**
7. 판정된 문제(judge problems)가 1건 이상이면 2단계·3단계 문장만 work/angles.txt 에
   쓴다. 형식은 정확히 이것이다 — 두 헤더가 모두 있어야 하며 render.py 가 검사한다:

   ```
   ## 2단계
   <직무> 직무 -> 문제 N(<문제명>). <접점 1~2문장>
   ## 3단계
   주목 1. <1단계의 항목명 그대로>
   이 사항을 지원동기로 쓴다면
     - <방향성> (매핑 테이블: [<유형> × <직무계열>])
     - <방향성> (매핑 테이블: [...])
   구체화 참고 — <KIPRIS 키워드·회사 숫자로 좁힌 한 문단, 있을 때만>
   ```

   2단계는 문제당 한 줄, 전체 260자 이내 (방향성 목록은 쓰지 않는다).
   2·3단계에 쓰는 수치는 1단계(render 가 만든 문제 목록)에 있는 것만 쓴다 —
   dart.json 을 뒤져 새 숫자를 꺼내오지 않는다. 3단계 "주목 N." 제목은 1단계의
   항목명을 그대로 쓴다.
   3단계 방향성은 **지원 직무 계열 열의 칸만** 쓴다 — 영업이면 [× 영업·마케팅]만.
   옆 열(기획·전략, 재무·구매 등)을 끌어오지 않는다. render.py 가 검사해 중단한다.
   3단계 방향성은 **매핑 테이블 골격 문구를 그대로 쓰고** 회사 숫자·KIPRIS 키워드
   한 구절만 덧붙인다 — 항목당 95자 이내, 명사구. "~에 기여하고 싶다", "~하겠다"
   같은 1인칭 문장은 자소서 문장이라 금지다(문장은 사용자가 쓴다).
   예: "- 대체 소재·내재화 기술 연구 — 소맥분·팜유 등 수입 원재료 (매핑 테이블: [의존 × R&D])"
   3단계가 없거나 비어 있거나 위 규칙을 어기면 render.py 가 중단하고 이유를
   출력한다 — 그때 angles.txt 를 고쳐 재실행한다. **0건이면 angles.txt 없이 render.py 를
   실행한다** — `--angles` 만 빼면 render.py 가 "판정된 문제가 없어 방향성을 제시하지
   않습니다"로 채운 리포트를 만든다. 0건은 리포트를 안 만드는 이유가 아니다.
   리포트를 만들지 않는 경우는 dart.json 자체가 실패(ok=false)했을 때뿐이다.
   그다음 `scripts/render.py work/dart.json work/judge.json work/kipris.json
   --job "<직무>" --angles work/angles.txt --out work/draft.txt` 로 리포트 전문을
   만든다. 1단계·[출처]·[판정 기준]·[특허 동향]·[더 볼 것]·[저장]은 render.py 가
   JSON 에서 만든다 — Solar 가 쓰지 않고 고치지도 않는다.
   이어서 `scripts/verify.py work/draft.txt work/dart.json work/judge.json
   work/kipris.json` 실행 — 이슈가 있으면 angles.txt 의 해당 문장을 원본 값으로
   교체하거나 삭제하고 render → verify 를 다시 돈다. pass=true 일 때만 다음으로.
   투자 확대 판정 시·R&D 계열 직무 시 KIPRIS 키워드로 방향성을 구체화한다
8. 통과한 최종 리포트 전문을 **작업 공간 루트**에
   why-this-company_{회사명}_{직무}_{YYYYMMDD}.txt 로 저장한다.
   스킬 폴더(.pi/skills/…)는 숨김 폴더라 사용자 파일 목록에 보이지 않는다 —
   루트에 있어야 입력창 옆 폴더 아이콘에서 바로 열린다.
   `WS_ROOT="$SKILL_DIR/../../.."` (스킬 폴더 기준 세 단계 위) 에 쓴다.
   저장한 파일을 `share_file` 도구로 다운로드 링크로 만들어 채팅에 붙인다.
   채팅에는 요약(발견 문제 유형·핵심 수치·방향성 개수) + 링크 + 저장 경로.
   전문을 채팅에 붙이지 않는다. 사용자가 다시 요청하지 않아도 링크로 바로 열 수 있어야 한다

## 스크립트 위치와 실행 방법 — 먼저 읽을 것

모든 `scripts/…`, `references/…` 경로는 **이 SKILL.md가 있는 폴더 기준**이다.
작업 공간 루트가 아니다. 스킬은 보통 `<workspace>/.pi/skills/why-this-company/` 에
설치되므로, 실행 전에 그 폴더로 이동한다.

```
SKILL_DIR=$(dirname "$(find . -path '*/skills/why-this-company/SKILL.md' | head -1)")
WS_ROOT="$SKILL_DIR/../../.."      # 작업 공간 루트 — 최종 리포트는 여기에 저장
cd "$SKILL_DIR" && mkdir -p work && python3 scripts/dart_client.py "농심" > work/dart.json
```

- 루트에서 `scripts/`가 안 보인다고 "스크립트가 없다"고 판단하지 않는다. 위 `find`로 먼저 찾는다.
- scripts/ 의 파일을 수정하지 않는다. 출력 문구가 마음에 안 들어도 코드를 고치지
  않는다 — [판정 기준] 문장을 바꾼 사고가 있었다. 고칠 것이 있으면 그 사실만 알린다.
- 스크립트를 못 찾았더라도 DART·KIPRIS를 직접 호출하거나 판정을 직접 하지 않는다.
  "스킬 스크립트를 찾지 못했습니다: <찾아본 경로>"라고 알리고 멈춘다.
- 중간 산출물 `work/` 는 스킬 폴더 아래(숨김). 최종 리포트 txt 만 작업 공간 루트에.

## 언제 어느 파일을 쓰는가

- `scripts/dart_client.py` — 2단계. DART 조회·재무·섹션 추출 (동적 데이터 연동)
- `scripts/kipris_client.py` — 3단계. 특허 출원 건수·키워드 (동적 연동, 실패해도 진행)
- `scripts/judge.py` — 4단계. 룰 판정. 직접 암산하지 않고 반드시 이 코드를 쓴다 (정확한 연산)
- `scripts/render.py` — 7단계. judge/dart/kipris JSON + angles.txt 로 리포트 전문 생성.
  형식·절 순서·0건 처리를 코드가 고정한다 (출력 형식 보장)
- `scripts/verify.py` — 7단계. 리포트의 모든 수치를 원본과 재대조 (출력 형식 보장)
- `references/reference.md` — 6단계. 유형×직무 매핑 테이블과 데이터 소스 표
- `references/output-example.md` — 리포트 작성 직전. 출력 형식의 원본
- `scripts/scripts.md` — 스크립트의 동작·설계 근거를 확인해야 할 때
- `assets/` — 현재 사용하는 양식 파일 없음 (assets/assets.md 참고)

## 출력 형식

references/output-example.md 의 3단계 구조를 그대로 따른다:

1단계 — 문제 목록:
[잘하고 있는 것] → [그럼에도 남는 문제] 번호별 (판정: 유형 — 조건) 표기
→ [확인 결과 특이사항 없음] → [자동으로 읽지 못한 항목]
2단계 — 지원 직무와 닿는 지점 (문제와 직무의 접점을 1~2문장으로)
3단계 — 문제별 "지원동기로 쓴다면" 방향성 2-3개 (매핑 테이블 좌표 표기)
→ [출처] → [판정 기준] → (선택) [특허 동향] → [더 볼 것]

리포트 전문은 render.py 출력 그대로다. Solar 가 쓰는 부분은 angles.txt 의
2단계·3단계뿐이며, 거기에도 아래 규칙이 적용된다. render.py 가 만든 절을
다시 쓰거나 순서를 바꾸거나 절을 추가하지 않는다.
판정된 문제가 0건이면 render.py 가 "판정된 문제가 없어 방향성을 제시하지 않습니다"로
채운다 — 판정 불가 항목을 문제로 포장하거나, 판정 안 된 유형의 매핑 칸을 쓰지 않는다.

리포트에서 판정 결과를 부르는 말은 "주목할 사항"이다 ("문제"라고 쓰지 않는다 —
투자 확대처럼 문제가 아닌 유형도 있고, 자소서 어휘로 이어지기 쉽다). 번호는 "주목 1.".

리포트 표현 규칙:
- 판정 결과는 judge 출력을 그대로 옮긴다. 다시 판단하거나 다른 유형의 기준을
  섞지 않는다. status=미판정 → [확인 결과 특이사항 없음]에 "해당 없음 — 이유",
  status=판정 불가 → [자동으로 읽지 못한 항목]에만. 한 유형을 두 절에 넣지 않는다.
  "아직 문제 없음", "판정 근거로 쓰지 않음" 같은 임의 표현을 쓰지 않는다.
  [판정 기준]은 아래 표준 문장 그대로 쓴다 (예: 투자 확대에 ±10%p를 붙이지 않는다).
- 금액은 조와 억을 함께 쓴다: "3조 5,143억". "3조 원", "4조"처럼 조 단위로
  반올림하지 않는다 (verify가 이슈로 잡는다). 영업이익 등 억 단위 금액도 같다.
- 접수번호는 "rcpNo" 한 가지로만 표기한다.
- 2단계는 2문장 이내. 방향성 예시를 나열하지 않는다 — 방향성은 3단계에만 쓴다.
- 비중이 "합계 대비 계산"으로 표시된 경우(비율 열이 없는 표) 판정 문장에
  "표에 비율 열이 없어 합계 대비로 계산했습니다"를 덧붙인다.
- "미판정", "판정 불가", "파싱", "섹션", "룰" 같은 내부·기술 용어 금지.
- [확인 결과 특이사항 없음]: 검토했으나 문제로 잡히지 않은 유형을
  항목별로 "해당 없음 — 이유 한 줄"로 보여준다. 숨기지 않는다.
- [자동으로 읽지 못한 항목]: "보고서의 표 형식이 회사마다 달라
  자동으로 읽지 못했습니다. 원문에서 직접 확인해 주십시오:
  II. 사업의 내용 > N. 항목명 (+링크)" 형태로 안내한다.
- "하지 않은 것" 류의 원칙 낭독 절은 리포트에 넣지 않는다.
- 작업 로그를 리포트에 붙이지 않는다. "작성 근거 요약", "내부 확인용",
  "검증 결과", "판정 결과" 같은 절을 만들지 않는다. 위 3단계와 [출처]·
  [판정 기준]·[특허 동향]·[더 볼 것] 외의 절은 출력하지 않는다.
  verify 실행 여부·이슈 건수·PASS 여부는 내부 절차이므로 사용자에게 쓰지 않는다.
- 같은 수치는 리포트 안에서 한 가지 표기로만 쓴다. 본문과 다른 절에서
  값이 갈리면 verify를 다시 돌린다.
- 링크는 실제 URL 전체를 출력한다. "(원문 링크)" 같은 자리표시 문구를
  그대로 내보내지 않는다. rcpNo가 있는 곳은 전부
  https://dart.fss.or.kr/dsaf001/main.do?rcpNo=<실제값> 형태로 쓰고,
  URL을 모르는 문서(지속가능경영보고서 등)는 DART 검색 경로로 안내한다.
- [출처]: 사업보고서(연결 기준, 제N기, rcpNo 링크, 문제별 세부 항목명).
  기수(제N기)는 dart.json의 period_no 값이 있을 때만 쓴다. 없으면 기수를
  빼고 "연결 기준, 2025년 사업보고서"처럼 사업연도로 쓴다. 기수를 추정하지 않는다.
  + KIPRIS(표기한 경우, 분석 판단 미사용 명시) 모두 나열.
- [판정 기준]: 이번 리포트에서 확인·적용된 기준을 쉬운 말로 나열 (쏠림/급한 변화/소수 거래처 의존/성장 정체/투자 확대/수익성 악화 — render.py 가 출력).
  유형명도 쉬운 말: 쏠림 / 급한 변화 / 소수 거래처 의존 / 성장 정체 / 투자 확대.
- 방향성 말미에 "방향성의 선택은 지원자 본인의 몫"임을 명시한다.
- 이모지·장식 기호는 쓰지 않는다.
- 최종 리포트 전문은 채팅에 출력하지 않는다. verify를 통과한 최종본을
  작업 공간 루트의 why-this-company_{회사명}_{직무}_{YYYYMMDD}.txt 로 저장한다.
- 저장 파일의 내용은 리포트 제목 첫 줄부터 [저장] 줄까지다. 그 뒤에 아무것도
  쓰지 않는다 — 작업 계획, 다음에 할 일, bash 명령, verify 실행 메모, 생각은
  파일에 들어가면 안 된다. 그런 것은 work/ 나 채팅에 남긴다.
  verify 통과 전에 루트에 쓰지 않는다 (초안은 work/draft.txt).
- 채팅에는 다음만 짧게 출력한다: 회사/직무 한 줄, 주목할 사항 유형과
  핵심 수치 각 한 줄, "확인했지만 해당 없음: …"(미판정만), "원문 확인 필요: …"
  (판정 불가만, 별도 줄), 제시한 방향성 개수, `share_file` 다운로드 링크,
  저장 경로([저장] 줄). 전문·표·[출처] 블록을 채팅에 붙이지 않는다.
  채팅 요약에도 "검증 결과", "파싱", "판정 불가" 같은 내부 용어를 쓰지 않는다.
  링크 생성이 실패하면 경로만 남기고 실패 사실을 한 줄 덧붙인다.
- 채팅 응답은 [저장] 줄에서 끝난다. 그 뒤에 "스킬로 저장해둘까요", "도움이
  되셨다면", "더 필요하시면" 같은 제안·마무리 인사·추가 안내를 붙이지 않는다.
  자소서 대필 불가 안내는 사용자가 문장 작성을 요청했을 때만 한다.
- 예외는 하나 — 파일 저장이 실패했을 때만 전문을 채팅에 출력한다.
  리포트가 어디에도 남지 않는 상황을 만들지 않는다.

## 하지 않는 일

- 자소서 문장을 대신 쓰지 않는다 (방향성까지만). "문장은 따로 써드릴게요" 같은
  예고도 하지 않는다
- 스킬 규칙 밖의 "별도 도움"을 제안하지 않는다. 판정 0건이면 0건 리포트를 만들고
  끝낸다. 사람 손으로 보강하자는 선택지를 내밀지 않는다
- 판정을 멈추고 사용자에게 선택지를 묻지 않는다. 2~8단계는 한 번에 끝까지 간다
- 사용자의 경험을 지어내지 않는다
- 공시에 없는 숫자를 만들지 않는다 (모든 수치에 출처, verify 통과 필수)
- 숫자의 원인을 해석하지 않는다 / 기업 평가·지원 여부를 추천하지 않는다
- 웹 검색을 하지 않는다 (최신동향은 v2 — web-research 스킬 연동)

## 예외/실패 대응

- 기업명 미매칭·오타 → dart_client가 반환한 유사 후보를 보여주고 재입력 요청
- 비상장사·보고서 없음 → 공시 의무가 없음을 명시하고 종료
- 표 파싱 실패(judge의 "판정 불가") → 숨기지 않고 "이 항목은 원문 확인 필요"
  + rcpNo 링크로 안내
- API 무응답 → 스크립트가 5초 후 1회 재시도, 실패 시 사실대로 보고
- 3개년 중 일부만 존재 → 비교 불가 명시, 존재하는 연도만 제시
- 직무가 6계열 밖(HR·디자인 등) → 공시 기반 방향성 도출이 어려움을 명시,
  문제 목록(1단계)까지만 제공
- 직무 미입력/"모르겠음" → 직무를 한 줄로 되묻는다. 직무 추천은 안 함. 직무 없이는 실행하지 않는다
- KIPRIS 키 없음·검색 0건 → "특허 정보 확인 불가" 표기 또는 생략, 본편은 계속
- verify 이슈 발생 → 해당 문장 교체·삭제 후 재검증. 통과 전 응답 금지


## 키

OPEN_DART_API_KEY, KIPRIS_API_KEY 는 타임리 설정 > 환경변수에서 읽는다. 하드코딩 금지,
.env·키 파일·.cache/·work/ 와 생성된 리포트 txt 는 제출물에 포함하지 않는다.
